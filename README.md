# 直播节目串联单

用 Python Flask + SQLite + 原生 JavaScript 实现的直播节目串联单（rundown）工具。

## 快速开始

```bash
docker compose up --build
```

启动后在浏览器打开：**http://localhost:8000**（端口 `8000`）。

- 首次启动自动创建 SQLite 数据库（容器内 `/data/rundown.db`，通过命名卷 `rundown-data` 持久化）。
- 重启容器后仍可查看实况与待播排期。
- 停止：`docker compose down`（加 `-v` 会连同数据一起删除）。

### 本地开发（不用 Docker）

```bash
pip install -r requirements.txt
python app.py
```

同样访问 http://localhost:8000 。数据库默认写在 `./rundown.db`，可用环境变量 `DB_PATH`、`PORT` 覆盖。

## 使用流程

1. **创建节目**：设置节目起点（日期时间）与总秒数，按播出顺序录入清单：
   - 赞助段：固定时长；
   - 访谈段：最短 / 目标 / 最长秒数。
   提交时自动排程，无法恰好排满总时长会给出差额并拒绝创建。
2. **直播进行**：页面显示每段预计起止时间、当前段、已播 / 剩余时长与预计终点。
   每结束当前段，录入实际秒数并确认；系统按实际已播总时长重排余下清单。
3. **编辑待播清单**：一次编辑整份未播清单，可插入、删除、移动访谈段，
   或调整访谈段的最短 / 目标 / 最长秒数；赞助段的时长与先后顺序不可变。
4. **备播方案**：在“编辑待播清单”中排出另一种访谈编排，填写名称后点“存为备播方案”。
   保存与查看都不改变正在播出的清单；页面中的备播卡片按最新实播记录重算各段起止时间，
   若已无法恰好排满会同时显示差额。点“启用备播”时系统校验：
   保存后已播的段是备播原清单中同序的开头、备播引用的其余旧段仍待播、
   赞助段与现行待播赞助一致、按最新实播时长能排到节目终点；
   任一不满足则说明原因且不作任何改动，全部通过则一次性替换待播清单与排期，
   并清除已解决的冲突，之后仍可照常录入实播和编辑。
   备播方案持久化保存，重启后仍可查看；重置节目时一并清除。
5. **重置节目**：删除整档节目与全部记录（含备播方案），重新开始。

## 排程规则

- 剩余时间 = 节目总秒数 − 实际已播总秒数。
- 先沿用各访谈段的目标时长（赞助段为固定时长）；
  差额按清单顺序在各访谈段的 [最短, 最长] 范围内分摊：
  有富余则从前到后依次拉长（至多拉到最长），超时则从前到后依次压短（至多压到最短），
  使待播清单恰好排到节目终点。
- 无法排满或仍然超时：返回具体差额（“仍差 X 秒” / “超出 X 秒”）并**拒绝**此次创建或编辑。
- 录入实际秒数导致余下清单无解时：**已播记录必须保留**，页面显示冲突横幅与差额，
  待播段暂按目标 / 固定时长展示，可再次编辑待播清单解决冲突。
- 已播记录不可改写。
- 备播方案保存时沿用同一套赞助约束与排程规则；保存后实播继续推进，
  备播卡片中的起止时间与可启用状态会按最新实播记录实时重算。

## 接口简介

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 单页应用 |
| GET | `/api/state` | 当前实况、待播排期与备播方案 |
| POST | `/api/show` | 创建节目与初始清单 |
| POST | `/api/segments/complete` | 结束当前段，录入实际秒数 |
| POST | `/api/rundown/edit` | 整体替换待播清单（赞助段锁定） |
| POST | `/api/backup` | 保存 / 覆盖备播方案（命名），不改变现行清单 |
| POST | `/api/backup/apply` | 启用备播：校验通过后一次性替换待播清单与排期 |
| POST | `/api/show/reset` | 删除整档节目（含备播方案） |
